Route: I — symmetric-conductance matrix-free backend
Question: Does the symmetric positive-conductance subfamily provide a genuinely GPU-capable, memory-bounded alternative to directed sparse LU, and what expressivity is lost?
Precise claim/hypothesis: With one strictly positive conductance per undirected edge incident to the interior, the reduced Dirichlet graph Laplacian is symmetric positive definite. A batched edge-scatter operator therefore admits matrix-free conjugate gradients for both forward and identical adjoint systems. Custom implicit differentiation needs only conductances, the converged primal, boundary values, and constant-size Krylov work vectors; it does not store an iteration tape. Boundary-boundary conductances are excluded because they cannot affect the interior harmonic extension.
Assumptions: a connected certified triangulated disk, nonempty Dirichlet boundary, positive finite conductances, a convex ordered target boundary, and forward/adjoint residuals tight enough for the requested dtype.
What would falsify it: a nonpositive reduced quadratic form, failure of the edge operator against an independently assembled dense Laplacian, CG residual or adjoint identity failure, gradient disagreement with dense autograd/finite differences, hidden sparse assembly/factorization, topology failure in returned dtype, or memory growth proportional to iteration count.
Smallest decisive test: on a nonsquare 4-by-3 structured disk, compare matrix-free products and solutions with a dense SPD reference; run double gradcheck for conductance logits and boundary; instrument that SciPy factorization is never called and that only a constant number of state-sized tensors are retained.
Prior work: classical weighted Tutte embeddings and Dirichlet graph Laplacians; Phase V Route I-C/D; the directed direct oracle implemented earlier in this phase.

Topology-theorem result (2026-09-21T16:56:00Z): The exact missing weak-convex theorem was identified as Floater (2003), Theorem 6.1: for a triangulated disk and a positive convex-combination map whose boundary maps homeomorphically to a convex region, injectivity is equivalent to excluding any dividing edge (a non-boundary edge joining boundary vertices) whose image lies in the target boundary. Thus collinear rectangle-side subdivisions are admissible, but the dividing-edge clause is essential. `DirectedTutteSystem` now performs a one-time combinatorial disk certificate (unique/all-used simplices, coherent edge incidence, connected face complex, interior-cycle/boundary-path vertex links, one boundary cycle, Euler characteristic one), an exact dyadic-integer source realization/simple-boundary check, and caches dividing edges for a pre-solve target-boundary test. It also rejects reuse with a same-size but different mesh. Thin structured rectangles remain accepted. Independent implementation review ran the specified 35-test set, checked 20 independent square chords and all required grid sizes, and returned PASS. This closes the fixed-input floating-representation source and Floater hypotheses; it does not turn legacy pre-cast target diagnostics into exact real-arithmetic statements.

Boundary result (2026-09-21T16:56:00Z): The four independent per-side softmax distributions, exact shared corners, and `H_min + softplus(m)` modulus pass double gradcheck and random broadcast/finite-difference checks. Independent review exposed that positive softmax entries alone do not ensure representably distinct cumulative vertices, registered-buffer tuples become stale after device migration, inverse softplus overflowed for large heights, and a large finite float32 modulus could realize an infinite height. Red regressions now require strict order of the actually realized coordinates, query registered side buffers dynamically, use a stable inverse softplus, and reject nonfinite realized height. Combined verdict: PASS, `42 passed, 1 CUDA-unavailable skip`; meta-device migration was verified, while real GPU execution remains to be measured remotely.

Directed matrix-free result (2026-09-21T17:10:00Z): `MatrixFreeDirectedTutteLayer` applies (A=I-P_{II}) by neighbor gather/weighted reduction and (A^T) by scatter-add, with vectorized batch/two-coordinate BiCGStab and a custom implicit adjoint. It assembles no CSR, performs no factorization, and saves probabilities plus one independent primal rather than the Krylov trajectory. Independent normal-scale dense and directional checks passed, including an irregular nonsymmetric disk. The first review nevertheless found a serious scale-dependent false certificate: squared residual norms underflowed after an iteration, reporting zero residual and corrupting tiny-cotangent gradients. Every norm and dot product now uses component scaling and explicitly rejects unsafe rescaling/subnormal cases; true residual reporting no longer clamps a small denominator. Original float64/float32 raw 3-by-3 and irregular-disk probes now either solve accurately or fail closed with a nonconverged report. Focused result: `39 passed, 2 CUDA-unavailable skips`; independent verdict: PASS for the bounded CPU numerical scope. Arbitrary-scale availability, actual CUDA behavior, and GPU performance remain unverified until remote execution.

Symmetric matrix-free result (2026-09-21T17:47:00Z): `MatrixFreeSymmetricTutteLayer` assigns a strictly positive softplus conductance to every active undirected edge and applies the reduced SPD Laplacian by edge scatter, with a vectorized two-coordinate CG primal and an implicit transpose-identical adjoint. Per-sample conductance normalization is kept inside autograd so global-scale gauge invariance and its VJP are preserved. Independent review first falsified the implementation on huge upstream adjoints and boundary-only empty conductance sets; per-RHS max-absolute scaling, scaled absolute tolerances, finite reconstruction checks, and an explicit empty-edge branch close both cases. Question: Why do CPU-verified matrix-free solvers fail during the first realistic 17-by-17, 256-squared CUDA optimization, and can the failure be removed without hiding residual error or storing iteration histories?
