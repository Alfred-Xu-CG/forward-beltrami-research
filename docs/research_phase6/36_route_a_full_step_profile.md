# Route A：百万控制顶点完整图像层的分项前向计时

## 为什么分项测量

热启动总forward/VJP已经证明1025²控制层可运行，却不能说明瓶颈在图像编码器、全细面安全检查、稠密点插值还是图像采样。本节在**保持同一输出和同一反向路径**时，在每个前向组件之后做CUDA同步并记录该组件的墙钟；它是定位计算热点的测量，不是把各行当作独立算法或独立kernel的理论下界。因多次同步、Python调用及计时误差，分项中位数相加不必严格等于整次前向中位数。

输入是一对512×512灰度图；已训练编码器先从二图推断257²粗潜在变量，粗安全解码器产生固定边界的257² P1同胚；精确P1细分到**1,050,625个1025²控制顶点**、2,097,152个原面，接着用两次图像条件的16模态细反馈和QC/面积证书生成最终细P1同胚。在262,144个最终像素位置查询一次映射，采样移动图一次，和固定图取image MSE并把损失回传至编码器。这里还为了评估额外计算了一次 coarse→fine 基底和一次训练期最小面积扫描；可部署版本若不需要这两个诊断张量可以删去这项开销，但未在此报告未经测量的节省。

同一AI主机空闲物理GPU7、float32、batch1、high64目标、冻结A8编码器、默认仅checkpoint细安全更新、20次完整 forward/VJP，无参数更新；先评价一张保留图再热身，丢第一次，其余19次各分项和总数取中位。32张训练图与1张保留图常驻GPU。完整层每次还拒绝输入/输出的非有限、错误边界、非正面积或超出规定QC cap 的情形。GPU7是与[batch扩展实验](33_route_a_million_control_batch_scaling.md)中GPU3相同型号的A6000，但不是同一物理卡，不能从几毫秒差推断重算策略变化。

| 前向组件 | 中位耗时 | 包含的实际工作 |
|---|---:|---|
| 图像编码器 | 3.46 ms | 输入图像拼接与CNN生成粗latent |
| 粗P1安全解码 | 24.86 ms | 257²构造、图像反馈与粗QC/面积约束 |
| 粗→细基底表 | 0.28 ms | 再计算一份精确细分基底供评估；层内部随后亦会细分 |
| 两次细反馈和全面证书 | **50.28 ms** | 图像提示、16模态谱化、细顶点安全更新及全部细面检查 |
| 最终坐标查询 | 0.13 ms | 1025² P1映射在512²像素处插值 |
| 移动图 warp | 0.07 ms | 双线性采样移动图一次 |
| 图像MSE | 0.07 ms | 像素残差平方平均 |
| 额外训练期面积扫描 | 0.48 ms | 冗余诊断，不属于细层内部证书 |

测得完整前向81.98 ms、整个图像损失至编码器参数的VJP 206.88 ms，峰值PyTorch活动显存2.127GB。总反向时间**没有**分拆成组件，所以不能把细反馈前向50 ms推断为其VJP占比相同。分项结果清楚表明，该配置的主要前向成本在粗/细安全映射构造，尤其细反馈，不在最后的坐标插值或图像重采样；若要降延迟，优先改细反馈的光度提示、谱化、安全界与证书融合，而非仅优化最终512²查询。是否能在不削弱拓扑前提下减少证书成本、或用更少反馈pass达到同精度，尚未由此表证明。

原始设置与全部统计字段：`raw_results/a8_high64_1025_stageprofile_batch1_gpu7.json`。入口 `tools/phase6_exact_coarse_fine_feedback.py --profile-stages --use-module --passes 2 --fine-cycles 64 --benchmark-repeats 20 --batch 1`；不要把此表的逐段同步计时同未逐段同步的[32节](32_route_a_activation_memory_tradeoff.md)或[33节](33_route_a_million_control_batch_scaling.md)相减作微秒级性能判断。
